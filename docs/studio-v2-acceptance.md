## Mock

```bash
.venv/bin/python -m unittest discover -s tests -t .
```

结果：`Ran 28 tests in 0.643s`，`OK`。

覆盖：

- 图片 1024 和 2048 的创建体、预览和下载代理。
- 视频文生、图生、首末帧各一次创建，请求体含对应的 data URL。
- 创建失败不自动重试。
- `queued`、`running`、`succeeded`、`failed`、`needs_review`。图片的 `submitting` 显示为生成中。
- 局域网绝对签名 URL 改写到配置的 8090，查询字符串保留。
- 8189、8190、8089 以及其他端口的下载地址不会被请求。
- 302 不跟随。
- 每次下载前重新查询签名。
- 响应和页面不含 API Key。
- 旧 `/api/v1/tasks` 与旧 `/api/tasks` 已不存在。
- 不写入 Studio 输出目录。
- `.env` 准备不会复制旧 Native API 密钥或 SQLite 路径。

这些测试使用假的上游或本机临时端口，不是 104 上的模型输出。

同一天又在本机用临时假上游打开了页面：1024 和 2048 都出现预览，下载响应是 PNG；文生视频可以播放，下载响应是 MP4。图生和首末帧只核对了上传区是否出现，没有在浏览器里选择真实图片文件。刷新后 3 条记录恢复，状态重新来自上游。页面、`localStorage` 和 Studio 响应都不包含测试密钥。假上游收到的创建请求是 2 次图片和 1 次视频；文件请求都落到配置的本机端口，没有发往 8189、8190 或 8089。这次播放的是测试文件，不是 104 模型结果。

运行时有一条 Starlette 关于 `httpx` / `httpx2` 的弃用警告，以及 TestClient 的访问日志。测试本身没有失败。
